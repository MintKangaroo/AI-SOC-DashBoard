### 어느 모듈이 어떤 근거로 탐지했나

`access_log_parser.classify_request()` 에 실제 로그 라인을 그대로 투입해 확인했습니다:

```
[탐지] HIGH  TLS 프로브 (HTTPS 스캔)  '\x16\x03\x01\x00î...' → 400
[탐지] HIGH  HTTP/2 프로브            'PRI * HTTP/2.0'      → 505
```

- `\x16\x03\x01` = TLS 1.0 record + ClientHello. 평문 HTTP 포트에 TLS 핸드셰이크를
  보내 "이 포트가 HTTPS 인가"를 확인하는 동작 (`access_log_parser.py:41`).
- `PRI * HTTP/2.0` = HTTP/2 connection preface. HTTP/2 지원 여부 확인 (`:45`).

**파싱된 32줄 중 31줄이 HIGH 로 분류됐습니다.** 탐지 로직 자체는 정상 동작합니다.

### AI/ML 판정 vs 최종 판정

**비교 불가입니다.** 이 이벤트들은 알림이 되지 못했으므로 AI 트리아지도 ML 분석도
받지 않았습니다(아래 참조). 제 판정만 적습니다.

- **판정: 정탐(TP), 그러나 악성은 아님.** 세 종류 프로브(TLS/HTTP2/평문)를 정확히
  같은 순서로 반복하고, 서로 다른 /24 에서 일주일에 걸쳐 각 IP 가 한 번씩만
  접근하는 패턴은 **인터넷 전수 스캐너**의 지문입니다. 특정 대상을 노린 공격이 아니라
  IPv4 전 대역을 훑는 서비스 인벤토리 수집에 가깝습니다.
- MITRE: T1595.002 (Active Scanning: Vulnerability Scanning) / T1046 (Network Service Discovery).
- **대응 불필요.** 차단해도 다른 /24 에서 다시 옵니다. 의미 있는 조치는 해당 포트를
  인터넷에 노출하지 않는 것입니다.

### SOAR 가 취한 조치와 그 타당성

**아무 조치도 없었습니다.** 알림이 생성되지 않았기 때문입니다. 결과적으로는
"차단하지 않음"이 옳은 결정이었지만, **옳은 이유로 그렇게 된 것이 아닙니다.**

### 이 사례로 배운 것 — 실제 탐지 31건이 조용히 사라진 원인

근본 원인을 코드에서 확인했습니다.

수정 전 코드(참고용 — 현재는 아래 "수정 완료" 대로 바뀌었습니다):

```python
def _collect_loop(self):
    first_pass = True
    while self.running:
        for src in self.sources:
            self._read_source(src, emit=not first_pass)   # ← 첫 적재는 emit=False
        if first_pass:
            first_pass = False

# _record_event 안
if not emit:
    return                    # ← MITRE·지도·SOAR 전부 건너뜀
```

`offset` 초기값이 0이므로(`:93`) 대시보드는 **시작할 때마다 로그 전체를 읽습니다.**
그런데 첫 적재는 `emit=False` 로 돌고, `_record_event` 는 그 경우 통계만 올리고
**알림 생성 직전에 조기 반환**합니다.

의도는 이해됩니다 — 시작할 때 과거 로그 전체로 UI 를 폭주시키지 않으려는 것입니다.
하지만 구현이 틀렸습니다. **UI 표시를 억제하는 것과 탐지를 폐기하는 것은 다릅니다.**

확인 결과 이 13개 IP 는 `alerts.db`·`alerts_archive.db` 어디에도 **0건**입니다.

**정정**: 이 문서 초판은 "알림·인시던트까지 살아난다"고 적었으나 부정확했습니다.
확인 결과 `access_log_parser` 는 `threat_detector.report_alert()` 를 **아예 호출하지
않았습니다**(grep 0건). SIEM 파일 tail 이벤트는 라이브 모드에서도 알림이 된 적이 없고
MITRE·공격지도·SIEM 패널까지만 갔습니다. 아카이브의 `WEB_ATTACK` 은 `syslog_receiver`
에서 온 것이었습니다.

**수정 완료** (`fix/siem-backfill-loss`, 2026-08-27):

| | backfill (첫 적재) | live (이후) |
|---|---|---|
| 이벤트 목록·통계 | ✓ | ✓ |
| MITRE 매핑 | ✓ **(복구됨)** | ✓ |
| 실시간 스트림 | ✗ 요약 1건만 | ✓ |
| 공격 지도 | ✗ (실시간 지도라 과거 표시는 오독) | ✓ |
| SOAR | ✗ (지난 이벤트로 자동대응 금지) | ✓ |
| 알림 승격 | ✗ | ✓ **(신규)** |

- `emit` 불리언을 `mode`("backfill"/"live")로 대체해 "표시 억제"와 "탐지 폐기"를 분리.
- **offset 을 `data/siem_offsets.json` 에 영속화** — 이게 없으면 backfill 처리를 켜는

- HIGH/CRITICAL 외부 프로브를 알림으로 승격(`_promote_to_alert`). 위협유형은
  `PORT_SCAN`/`WEB_ATTACK`/`ANOMALY` 로만 매핑해 **자동차단 플레이북을 열지 않습니다**
  (PB-BRUTE-BLOCK 은 `BRUTE_FORCE`, PB-HONEYPOT-BLOCK 은 `HONEYPOT` 에만 반응).

## 사례 2 — 다중 프로토콜 서비스 탐색 (실제)

### 무슨 일이 있었나

2026-06-04 11:36, 단일 IP 가 4초 간격으로 **서로 다른 두 프로토콜**을 HTTP 포트에
시도했습니다.

```
06-04 11:36:09  45.33.109.***  "\x12\x01\x00/\x00\x00\x02\x00\x00\x00\x1a\x00\x06\x01..."  → 400
06-04 11:36:13  45.33.109.***  "\x03\x00\x00&!à\x00\x00þÊ\x00Cookie: mstshash="          → 400
```

### 어느 모듈이 어떤 근거로 탐지했나

`classify_request()` 의 `"\\x" in request` 규칙(`access_log_parser.py:43`)이
**바이너리 프로브 (프로토콜 스캔) · HIGH** 로 분류합니다.

### 페이로드 해석

- `\x12\x01\x00/...` — TDS(Tabular Data Stream) **pre-login 패킷**. 타입 `0x12` 는
  MS-SQL Server 의 PRELOGIN 메시지입니다. → **MS-SQL 서비스 탐색**
- `\x03\x00\x00&` + `Cookie: mstshash=` — TPKT 헤더 + X.224 Connection Request.
  `mstshash` 쿠키는 **RDP** 클라이언트가 보내는 고유 문자열입니다. → **RDP 서비스 탐색**

즉 "이 포트가 HTTP 가 아니라면 MS-SQL 이나 RDP 인가?"를 확인한 것입니다.

### 판정

- **정탐(TP), 정찰 단계.** 사례 1보다 표적성이 높습니다 — 무작위 스캐너는 보통
  프로토콜 하나만 시도하는데, 이 IP 는 두 개를 연속으로 시도했습니다.
- MITRE T1046 (Network Service Discovery).
- 다만 후속 접근이 없어 **침해로 이어지지 않았습니다.** 서버가 두 요청 모두 400 으로
  거절했고 해당 서비스가 실제로 열려 있지 않았습니다.

### SOAR 조치

**없었습니다** — 사례 1과 동일한 원인(첫 적재 폐기)입니다. 수정 후에는 이런 프로브가
`PORT_SCAN` 알림으로 승격되지만, **자동차단은 여전히 일어나지 않습니다** — 의도된
설계입니다(사례 1의 "수정 완료" 표 참조).

### 배운 것

바이너리 프로브 규칙(`"\\x" in request`)이 **의도치 않게 잘 동작했습니다.** TDS 나 RDP
시그니처를 명시적으로 작성한 적이 없는데도, 바이너리 페이로드라는 이유만으로 HIGH 로
잡혔습니다. 광범위한 규칙이 유용한 드문 사례입니다.

반대로 이 규칙은 **무엇을 탐색당했는지 알려주지 못합니다.** "바이너리 프로브"로만
표시되어 MS-SQL 인지 RDP 인지 구분되지 않습니다. 페이로드 앞부분으로 프로토콜을
식별하는 보조 분류를 넣으면 대응 판단이 쉬워집니다.

## 사례 3 — 메일/FTP 서비스 탐색 (실제)

### 무슨 일이 있었나

```
06-02 11:10:06  45.148.10.***  TLS ClientHello  → 400
06-02 11:10:07  45.148.10.***  "HELP"           → 400
06-02 11:19:32  31.14.254.***  "W\x00\x00\x00\x00\x11\x11\x07\x00\x00ÿÿ..."  → 400
06-08 14:01:01  5.226.140.***  "W\x00\x00\x00\x00\x11\x11\x07\x00\x00ÿÿ..."  → 400
```

### 판정 및 근거

- `HELP` 는 **SMTP·FTP·NNTP 공통 명령어**입니다. TLS 실패 직후 1초 만에 평문 `HELP` 를
  보낸 것은 "TLS 가 아니면 메일/FTP 서버인가"를 확인한 동작입니다.
- `31.14.254.***` 와 `5.226.140.***` 는 **바이트 단위로 동일한 페이로드**를 보냈습니다.
  서로 다른 대역의 두 IP 가 같은 도구를 쓴다는 뜻이며, 6일 간격(06-02, 06-08)으로
  같은 스캔 캠페인이 반복됐음을 시사합니다.
- **정탐(TP), 정찰.** 침해 없음.

### 탐지 상태 — 여기서 미탐이 나옵니다

| 요청 | 분류 결과 |
|---|---|
| TLS ClientHello | ✅ HIGH — TLS 프로브 |
| `W\x00\x00...` | ✅ HIGH — 바이너리 프로브 |
| **`HELP`** | ❌ **미탐** — `LOW / 클라이언트 오류 (HTTP 400)` |

`HELP` 는 바이너리가 아니고 키워드 목록(`/.env`, `/wp-`, `/admin` …)에도 없어
`status >= 400` 포괄 규칙(`access_log_parser.py:59-60`)으로 떨어집니다.

**같은 IP 의 같은 스캔 세션인데 한 요청은 HIGH, 한 요청은 미탐입니다.** 상관관계
분석이 붙어 있었다면 묶였을 텐데, 알림 자체가 생성되지 않아 그 기회도 없었습니다.

### 왜 걸러지지 않았나

1. **IP 가 진짜라서.** 시뮬레이터가 실존 공격자 IP 를 사용했기 때문에 IP 평판 조회
   (AbuseIPDB)도 "악성"으로 답했을 것입니다. 평판 가중치가 오히려 신뢰도를 **올렸습니다.**
2. **`details.demo` 플래그가 없어서.** `authlog_parser` 는 데모 모드일 때만 플래그를
   심는데, 이 경우는 `DEMO_MODE=False` 인 **실모드**였습니다. 시뮬레이터 로그를
   실로그로 읽었으니 코드 입장에서는 진짜였습니다.
3. **로그 출처를 검증하는 단계가 없어서.** 파일 경로만 믿고 내용의 신빙성을 묻지 않습니다.

### 이 사례로 배운 것 / 어떻게 고쳤나

**이것이 이 문서에서 가장 중요한 사례입니다.** 데이터 출처를 검증하지 않으면
관제 시스템이 자기 자신의 테스트 데이터를 침해 증거로 승격시킵니다. 알림 11만 건,
인시던트 2만 3천 건이 그렇게 쌓였습니다.

고친 것과 남은 것:

- ✅ **알림 origin 구분** — `alerts` 테이블에 `origin`(real/demo/legacy) 컬럼이 이미
  있습니다. 다만 `demo` 플래그가 8개 데모 경로 중 일부에만 설정되어 신뢰할 수 없습니다.
- ⬜ **로그 소스 신빙성 표시** — `SIEM_ACCESS_LOGS`/`AUTH_LOG_PATH` 항목별로
  `trusted|simulated` 를 명시하고, simulated 소스에서 온 알림은 `origin="simulated"`
  로 강제하는 방안. **미구현 — 다음 작업 후보입니다.**
- ⬜ **파일 헤더 자동 감지** — 첫 줄에 `# SIMULATED` 가 있으면 경고를 띄우고
  해당 소스의 알림을 자동으로 `simulated` 로 표시. 구현 난도 S.

### 부수 발견 — 우연의 일치 주의

시뮬레이터가 쓴 `45.148.10.35` 와 사례 3의 **실제** 스캐너 `45.148.10.200` 은 같은
/24 입니다. 우연이지만, `45.148.10.0/24` 가 실제로 악용되는 대역이라 시뮬레이터가
현실적인 값을 골랐기 때문입니다. **같은 /24 라는 이유로 두 사건을 한 캠페인으로 묶으면
안 됩니다** — 하나는 합성, 하나는 실제입니다.

## 사례 5 — 미탐: 웹 공격 페이로드가 분류를 통과

### 무슨 일이 있었나

실제 로그에서 발생한 사건은 아니고, 사례 3의 `HELP` 미탐을 계기로
`classify_request()` 를 점검하다 발견했습니다. 실제 함수에 투입한 결과입니다.

```
[미탐] LOW   클라이언트 오류(404)  'GET /../../etc/passwd HTTP/1.1'          → 404
[미탐] INFO  정상 요청             'GET /../../etc/passwd HTTP/1.1'          → 200
[미탐] INFO  정상 요청             "GET /?id=1' OR '1'='1 HTTP/1.1"          → 200
[미탐] INFO  정상 요청             'GET /?q=<script>alert(1)</script>'       → 200
[미탐] LOW   클라이언트 오류(401)  'POST /api/login HTTP/1.1'                → 401
[탐지] CRITICAL 환경파일 탈취 시도  'GET /.env HTTP/1.1'                      → 404
```

### 왜 미탐인가

`classify_request()`(`access_log_parser.py:39-61`)의 키워드 목록은 **경로 기반 스캔**
8종(`/.env`, `/wp-`, `/admin`, `/phpmyadmin`, `/.git`, `/cgi-bin`, `/boaform`, `/shell`)만
다룹니다. **페이로드 기반 공격(경로 탈출·SQLi·XSS)에 대한 규칙이 없습니다.**

특히 심각한 조합:

> **경로 탈출이 200 으로 성공하면 "정상 요청"으로 분류됩니다.**

공격이 실패했을 때(404/400)는 `LOW`, **성공했을 때(200)는 `INFO`** 입니다.
심각도가 성공 시에 오히려 낮아집니다.

### 왜 이렇게 되어 있나

코드에 의도가 적혀 있습니다:

```python
# 일반 4xx/5xx 는 오탐이 많아 '의심'으로 올리지 않음 (프로브/스캔 패턴만 의심)
if status >= 400:
    return False, "LOW", f"클라이언트 오류 (HTTP {status})"
```

오탐 억제 자체는 타당한 판단입니다. 문제는 **상태 코드로만 거르고 요청 내용을 보지
않는다**는 점입니다.

### 고칠 방향

상태 코드 판정 **앞에** 페이로드 패턴 검사를 넣습니다. 상태 코드와 무관하게 평가하되,
성공(2xx)일 때 심각도를 올립니다.

```
../  ..%2f  ..%5c        → 경로 탈출        (2xx면 CRITICAL, 그 외 HIGH)
' OR   UNION SELECT   --  → SQL 인젝션 시도  (2xx면 CRITICAL, 그 외 HIGH)
<script  javascript:  onerror=  → XSS 시도
;cat  |sh  $(  `        → 명령 인젝션 시도
```

**미구현입니다.** `docs/detection_rules.md` 에 반영하고 회귀 테스트와 함께 넣어야
합니다. 규칙을 넓히면 오탐이 늘어나므로, 이번에 만든 중복제거·억제 레이어
(`modules/alert_dedup.py`)로 노이즈를 흡수하는 것이 전제 조건입니다.

## 종합 — 무엇을 배웠나

### 잡은 것

실제 인터넷 정찰 3건(IP 13개, 요청 64줄, 2026-06-02~08). 탐지 로직은 **31/32줄을
HIGH 로 정확히 분류**했습니다. TLS·HTTP/2·바이너리 프로브 규칙이 실데이터에서
의도대로 작동합니다.

### 놓친 것

| # | 문제 | 영향 | 상태 |
|---|---|---|---|
| 1 | 첫 적재가 `emit=False` 로 탐지 결과를 폐기 | **실제 HIGH 31건 전부 유실** | ✅ 수정 (`fix/siem-backfill-loss`) |
| 2 | `HELP` 등 평문 서비스 명령 미탐 | 같은 세션 내 일부만 탐지 | 미수정 |
| 3 | 경로 탈출·SQLi·XSS 규칙 부재 | 성공한 공격이 "정상 요청" | 미수정 |
| 4 | 시뮬레이터 로그를 실침해로 승격 | 알림 11만·인시던트 2.3만 오염 | 부분 (origin 컬럼) |

### 데이터가 부족합니다 — 정직한 보고

브리프의 우선순위(허니팟 → SSH 브루트포스 → 스캔/프로브 → 취약점 교차검증) 중
**실제로 발굴 가능했던 것은 "스캔/프로브" 하나뿐**입니다.

- **허니팟**: `HONEYPOT_BIND=100.64.140.27`(Tailscale). 공개 인터넷에 노출된 적이
  없어 실제 접촉 0건. 아카이브의 HONEYPOT 35,916건은 전량 데모 생성기 산출물.
- **SSH 브루트포스**: 실제 `/var/log/auth.log` 의 공격 0건. 아카이브의 11,661건은
  전량 시뮬레이터 재생.
- **취약점 교차검증**: nmap/ansible 스캔 결과가 DB 에 남아 있지 않아 사례 구성 불가.

또한 **AI/ML 판정 vs 최종 판정 비교는 어느 사례에서도 성립하지 않았습니다.**
실제 탐지 3건이 알림이 되지 못해 AI 트리아지를 받은 적이 없고, 전 시스템의
분석가 확정 판정은 1건뿐입니다(`docs/ml_models.md` 참조).

### 사례를 더 모으려면 — 구체적 제안

| 순 | 할 일 | 기대 수집량 | 난도 |
|---|---|---|---|
| ~~1~~ | ~~첫 적재 유실 수정~~ | ~~즉시 실제 31건 확보~~ | ✅ 완료 |
| 2 | `AUTH_LOG_PATH` 를 실제 `/var/log/auth.log` 로 전환 | 실로그 기준선 확보 (현재 공격 0) | S |
| 3 | 로그 소스에 `trusted/simulated` 표시 | 사례 4 재발 방지 | S |
| 4 | **허니팟을 공개 노출** (`HONEYPOT_BIND=0.0.0.0` + 포트포워딩) | 실측상 24~72시간 내 수십~수백 건 | M (선행조건 해소됨) |
| 5 | KR/USA 서버 access log 를 계속 수집 | 실측 주당 약 10건 (6월 기준) | 이미 됨 |

**4번의 선행조건이던 감사 항목 B-5(연결당 무제한 스레드)는 2026-08-27 해소됐습니다**
(`fix/conn-limits` — `HONEYPOT_MAX_CONNS` 기본 200, 초과분은 접촉만 기록 후 즉시 차단).
이제 공개 노출해도 스레드 고갈로 죽지 않습니다. 다만 노출 자체는 공격면을 늘리는
결정이므로, 방화벽에서 허니팟 포트만 열고 대시보드 포트(5055)는 닫혀 있는지
확인한 뒤 진행하십시오.

1번은 완료했습니다. 다만 **두 줄 수정이 아니었습니다** — offset 영속화가 없으면
재시작마다 전체를 재처리하므로 그것부터 만들어야 했고, SIEM 이벤트가 알림이 되는
경로 자체가 없어 승격 로직도 함께 넣어야 했습니다.

**부수 효과 하나를 밝혀둡니다**: backfill 이 MITRE 를 반영하게 되면서, 시뮬레이터
로그("허니넷")의 과거 탐지 23,952건도 MITRE 매트릭스에 들어갑니다. 라이브 모드에서는
이미 그렇게 동작하고 있었으므로 새로 생긴 문제는 아니지만, **사례 4의 근본 원인
(시뮬레이터 소스를 실소스로 취급)이 해소되기 전까지 MITRE 매트릭스는 합성 데이터가
지배합니다.** 3번(로그 소스 trusted/simulated 표시)의 우선순위가 그만큼 올라갑니다.

이제 가장 효과적인 것은 **3번**입니다.
